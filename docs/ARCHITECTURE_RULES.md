# 架构规范

版本：1.0  
更新：2026-10-24  
适用范围：浏览器站点、素材目录与导入工具、预览流水线、Electron 和原生 Windows 客户端。

本规范约束后续新增和修改的实现。[架构说明](ARCHITECTURE.md)描述当前入口，[架构评审](ARCHITECTURE_REVIEW_2026-10-23.md)记录已有债务。实际实现与回归结果是验收依据，文档不能作为“全站已完成模块化”的证明。

“必须 / 禁止”是变更要求；“应”是默认选择，偏离时需在提交说明中记录原因、影响范围和回归证据。用户明确的任务约束优先。历史实现可以分阶段迁移，但不得作为继续复制旧模式的理由。

## 1. 核心约束

| 编号 | 规则 | 验收依据 |
| --- | --- | --- |
| ARC-01 | 动画目录只在共同注册表登记，消费者不得另维护一份目录清单 | 注册表行为测试、架构检查 |
| ARC-02 | 同一引擎的游戏复用加载、采集、裁切与发布流程；差异进入数据或源适配器 | 新游戏变更范围、浏览器回归 |
| ARC-03 | 模型、皮肤、资源版本和预览必须可追溯；禁止借用其他模型的图片冒充成功 | 来源标识、预览策略与竞争测试 |
| ARC-04 | 视图、会话、资源访问、存储和渲染分别承担职责；共享服务使用显式接口 | 依赖审查、行为测试 |
| ARC-05 | 异步工作可取消、可超时，过期结果不得覆盖当前选择 | 快速切换、失败、取消测试 |
| ARC-06 | 生成结果经校验后发布；禁止通过改审计数字或放宽断言掩盖失败 | 原始诊断、图像检查、发布回归 |
| ARC-07 | 内容提交与站点上线有明确依赖，构建成功必须关联实际源提交 | Pages 发布契约、构建结果 |
| ARC-08 | 工作流只编排步骤和权限，实现留在可独立执行的脚本或应用模块 | 工作流契约、Windows 构建 |
| ARC-09 | 兼容页面 URL、模型 ID、收藏、缓存和桌面资源目录，迁移必须有策略 | 旧链接、旧数据、升级回归 |
| ARC-10 | 修复落到共同原因，验证覆盖行为与失败路径 | 对应回归用例、真实运行证据 |

## 2. 目录职责与依赖方向

| 边界 / 入口 | 负责 | 禁止承担 |
| --- | --- | --- |
| 页面 HTML 与样式 | 页面结构、可访问性、布局与共享设计变量 | 目录扫描、资源下载、缓存事务 |
| `assets/js/gallery/`、`assets/js/spine/`、`assets/js/live2d/` | 各页面交互、会话协调、视图与渲染适配 | 为每款游戏复制通用播放流程 |
| `assets/js/shared/` | 可复用的目录、身份、音频等服务，以明确输入输出暴露能力 | 隐式读取另一页面的 DOM 或可变全局状态 |
| `data/animation-catalogs.json` | 动画目录注册及目录元数据 | 单个模型的业务状态、截图结果 |
| 各目录 JSON / 数据文件 | 模型来源、引擎、皮肤、名称、预览与能力描述 | 可执行脚本、与实际资源不符的成功状态 |
| `scripts/catalog_registry.*` | 工具侧读取共同注册表与目录 | 按游戏维护另一套目录清单 |
| `preview_frame_pipeline.py`、`preview_policy.py` | 图像处理、质量与预览有效性规则 | Git 推送、页面渲染、游戏专属分支 |
| `preview_repository.py`、`preview_pipeline.py` | 来源校验、结果应用、CLI 编排 | 复制图像策略、绕开共同注册表 |
| `.github/workflows/` | 触发、依赖、分片、环境、权限和产物传递 | 大段业务算法、批量源码补丁实现 |
| `desktop/`、`native-desktop/` | 桌面宿主、原生适配和应用行为 | 依赖网页 DOM 来定义核心资源契约 |
| `native-desktop/build/` | 可单独执行的构建、装包与验收脚本 | 新增不可追踪的上游字符串替换链 |

依赖从入口指向服务，再指向适配器和外部资源。视图可以调用服务，服务不得反向操作具体视图。引擎差异封装在 Spine / Cubism 适配边界，来源差异封装在源适配器；通用服务不得通过游戏名称决定下载、裁切、缓存或发布算法。

新模块必须说明输入、输出、资源所有权、失败结果和释放方式。出现循环依赖时调整职责，禁止用新的全局变量绕过。仅供单一页面的 UI 辅助函数不必强行提升为共享服务。

当前经典脚本仍依赖有序加载和部分全局状态；迁移前必须明确这些依赖。新服务采用显式接口，逐步隔离存储、会话和视图后再迁移 ES Modules，不同时重写所有播放器。

## 3. 数据、身份与来源

1. 动画消费者必须从共同注册表读取目录。浏览器与 Node 共用注册服务，Python 读取同一注册数据；改变契约时同步跨语言回归。
2. 模型 ID 是兼容标识。角色、皮肤、常态/受损、全身立绘/战斗小人应明确区分；禁止仅凭同名或相似 ID 合并。
3. 目录总条数、去重后的可选外观数、成功播放数和有预览数必须分别统计。不得将“已建立索引”宣传成“全部可播放”。
4. 新来源应固定可追溯版本，记录原始 URL 和资源对应关系；更新来源必须重新校验骨骼、图集、贴图及版本兼容性。
   需标准化的旧设置保存为本地内容摘要版本，所有资源仍限定在固定上游；来源路径修正须唯一匹配并记录，补充动作限定在同一模型目录。设置内容变化必须使旧预览失效。
5. 预览有效性绑定实际资源身份，沿用共同的 `sourceIdentity` 契约。改变字段含义时，必须同步采集、发布、浏览器有效性判断和跨语言用例。
6. 数据结构发生不兼容变化时应引入版本和迁移，不得静默改变旧字段语义。审计与覆盖统计由工具生成，不能手改为全绿。
7. 名称、语音和来源映射应作为可追溯数据维护。不得继续把大块新映射塞入 UI 事件处理器；迁移旧映射时保留匹配优先级并验证变体。

## 4. 新增游戏与资源扩充

已有引擎的新游戏以“目录数据 + 注册 + 必需的源适配”接入：

1. 核验来源、版本、模型文件、纹理与动作，区分动态原画和战斗小人。
2. 编写或复用可重复执行的导入器，保证稳定 ID、去重、增量更新和失败记录；执行两次不得产生重复条目。
3. 目录登记到 `data/animation-catalogs.json`，禁止新增游戏专属自动截图或发布工作流。
4. 新来源在适配层补充明确的 URL、路径和版本规则，不得通过允许任意地址绕开验证。
5. 走统一预览流程，并验证代表模型的真实播放、缩放、切换和交互；未逐项验证的范围必须标明。
6. 动态来源覆盖范围在 `data/live2d-source-scopes.json` 声明，使用共同来源审计核对固定版本的完整范围；空范围、截断目录或网络失败不能标为完整。未索引源设置不等于缺失角色，须区分重复、资源不完整、质量筛选和未核验候选。
7. 静态导入同时维护原图、缩略图、身份与来源。覆盖报告区分“源中发现 / 已导入 / 校验失败 / 尚未核验”，未核对来源全集时不得宣称完整收录。

一次性修复脚本应注明用途及复现方式；常规更新不得依赖人工依次执行多个历史补丁。若差异无法通过已有数据表达，应先扩展来源或引擎契约，再接入新游戏。

## 5. 播放、交互与异步生命周期

- 可选模块的失败只更新该模块的状态；缓存不可用、语音 UI 订阅者异常及桌面消息接收端释放，不得把正常画布标记为播放失败或中断核心资源清理。故障必须保留诊断，真实的下载/格式/渲染错误仍按播放失败处理。
- 异步结果和输入回调同时校验当前会话/加载代次与资源实例归属；组件状态变更后丢弃过期结果。缓存事务由无 DOM 的存储服务负责，UI 不直接拥有数据库生命周期。

- 桌面同时显示的各个角色按游戏与模型 ID 分别拥有播放会话和可见状态，新增角色不得隐式关闭其他角色；隐藏、移除和取消只作用于目标身份。
- 每个播放会话拥有自己的加载请求、渲染器、音频和监听器；替换会话时释放旧资源。共享且昂贵的运行时可以缓存，但不得把旧角色状态带入新会话。
- 加载必须有总超时、取消和有限重试。区分来源不可达、格式不兼容、缺文件、渲染失败等原因，界面提供明确状态与重试。
- 切换模型、来源或动作后，仅当前会话可提交结果。取消应结束相关 Promise 与等待状态，禁止一直转圈。
- 自动化采集应读取明确的就绪/错误状态，禁止依赖中文提示文案判断结束。
- 语音匹配属于音频/动作服务。来源支持语音的交互应沿用同一解析规则，并在用户手势内启动播放；切换角色时停止旧音频。
- 无对应语音和播放被阻止必须如实区分，不能把无关动作语音绑定为“已修复”，也不能创建假成功状态。
- 动作适配必须保留源文件的循环语义；非循环动作结束后恢复明确的待机动作。按整个动作定义去重，不能只按文件名丢掉不同语音或淡入配置。命名与匿名动作组复用同一策略，手动切换可打断当前动作，过期请求不得回写。
- 同一模型的动作切换必须保留用户缩放、平移与会话取景；初始取景和显式适应画面才重新计算可见范围。屏幕像素检测只能在完整角色帧绘制后运行，不得把加载层或浮动 UI 纳入取景，也不得逐帧读取 GPU 像素。
- 释放必须核对实际运行时 API：旧版没有 dispose 时提供适配，确认已排队的回调不再绘制；模拟和绘制由同一个可暂停的会话时钟拥有。跨 iframe 修改脚本时同步提升父入口、iframe URL 与子脚本的共同版本，避免缓存混用。
- 缩放、拖动与适应画面使用统一坐标和边界规则。不得按游戏名称叠加裁切、偏移或模糊兜底来掩盖资源/渲染问题。
- MOC 声明画布不是可见网格的裁切范围；首次取景应覆盖有效网格，再做一次像素校准。网页底色与桌面透明表面分别验证，禁止通过删除白色服装、发色或场景像素处理背景。
- 保持引擎、资源和 CSS 显示尺寸的职责清晰；清晰度修复验证实际纹理、画布像素比和浏览器输出，不能只放大缩略图。

- 点击动作优先沿用有效的源点击区域和动作定义；仅能估算分区时必须标明。没有源互动动作的模型不得通过随机待机或攻击动作伪装支持。拖动、缩放及过期角色手势不得触发点击动作。

## 6. 存储、下载与兼容

- 缓存访问通过存储接口完成，页面不得同时管理 IndexedDB 事务和渲染生命周期。
- 缓存命中必须对应正确资源版本。新增版本键或清理策略时兼容历史数据库、收藏键和已下载资源，不得随仓库改名直接清空。
- 写入失败、损坏缓存、空间不足和取消均要有明确结果；提交完成前不得将资源标为已缓存。
- 新增或重构的下载器必须在流式接收期间执行大小、总预算、超时与取消约束，不能等完整响应进入内存后才检查体积。
- 不可信路径、解压目标和资源引用必须限定在预期根目录/来源范围内，禁止越界写入。
- 原生客户端升级复用有效资源和用户配置，程序更新与素材更新分别版本化，不能把重新下载全部素材作为默认升级方案。

既有下载器仍有接收后才检查大小的债务；上述要求约束新增和重构代码，不表示旧实现已全部符合。

## 7. 预览与发布事务

唯一默认预览入口为 `preview-pipeline.yml`，共同实现为 `preview_pipeline.py`、`preview_repository.py`、`preview_frame_pipeline.py` 和 `preview_policy.py`。旧游戏命名入口仅手动委托。

发布必须遵守以下顺序：

1. 根据注册表和共同策略生成待处理队列。
2. 真实加载对应模型，记录实际来源标识、成功帧或失败原因。
3. 转码并校验尺寸、图像内容及摘要；新截图按现有 360×420 契约生成，历史 480×360 由兼容策略核验。
4. 发布端读取最新 main，比较截图来源与当前模型来源，拒绝过期帧和无有效报告的候选。
5. 校验通过后替换文件和元数据；发布前运行集成检查，保持模型、文件、摘要和状态一致。
6. 以正常提交推送结果；遇并发更新重新校验或明确失败，禁止强推和静默覆盖。

模型级失败与流水线级失败分别报告。允许一轮成功发布部分合格预览，但必须保留未成功模型的诊断；不能用别的皮肤或静态图填充后称为动态帧。

## 8. 工作流、部署与权限

- 工作流保留编排，实现移入可独立运行的脚本。公共修复必须进入共同实现，不得只改某个游戏副本。
- 固定工具版本，明确输入、输出、失败条件、并发组和超时。发布权限只授予需要写入的任务，不向普通采集开放写权限。
- 所有自动内容发布器必须在 `deploy-content.yml` 中有明确的站点发布依赖。机器人提交不等于网页已更新。
- Pages 发布核验构建源包含目标提交；旧成功记录、正在构建、失败或超时均不得报告本次已上线。
- 目前发布契约是 main 根目录的分支式 Pages。变更分支、目录或发布模式时，必须同步发布服务、规范和回归。
- `workflow_run` 等带权限的后续流程仅消费受信 main，实现中不得直接执行不可信分支或下载产物内的脚本。
- 构建、发布和说明应记录源提交与实际验证范围；失败产物保留足够诊断，不输出凭据。

## 9. 桌面与上游适配

- 网页、Electron 与原生 Windows 是不同宿主，共用身份/来源等契约，不混用窗口、DOM 和命中测试实现。
- 原生行为写在应用模块或有明确版本的适配补丁中，构建逻辑放在 `native-desktop/build/`。
- 通用桌面协议只传目录身份，禁止任意网页/下载地址。网页运行时继续通过共同注册表和来源适配加载；新增同引擎游戏不得增加客户端白名单。合成视觉与命中掩模分开，限制采样频率、尺寸、区域数量并核对来源、会话和角色。旧协议与持久素材目录兼容；网站协议入口必须晚于对应二进制的成功发布。
- 固定上游版本；补丁必须检查锚点、唯一命中和预期结果，不得无限叠加不验证的字符串替换。
- 需要持续修改的原生渲染模块优先使用固定上游文件摘要约束的类型源码覆盖；整组输入预检通过后才能安装，发布包含完整模块、构建脚本与实际源摘要。不得无验证地静默覆盖新上游。
- 角色显示范围、透明区域命中、鼠标穿透和滚轮缩放必须分别验证；改变渲染边界要同时验证点击区域。
- 发布时验证安装、启动、更新、旧配置与资源复用。后续重构应让源代码包包含实际补丁结果或可核验的重建输入，不能只提供无法复现的上游版本说明。

## 10. 验证要求

| 改动类型 | 必须提供的验证 |
| --- | --- |
| 通用代码或目录契约 | `npm test`、`npm run check`、`npm run test:python`；相关行为和失败路径 |
| 身份、来源或预览策略 | 去重、版本变化、旧帧拒绝、完整 plan → convert → publish |
| 播放器、画布或手势 | 真实浏览器加载、切换、缩放、清晰度；取消和错误恢复 |
| 语音及互动 | 有声/无声来源、动作匹配、用户手势、切换取消；真实浏览器确认可播放 |
| 存储或下载 | 命中与失效、损坏与失败、取消、预算；保留旧数据的迁移验证 |
| 导入与覆盖 | 稳定 ID、重复运行、增量差异、失败明细；区分目录检查与实际播放 |
| 桌面行为或构建 | Windows 实际构建及相关资源、命中、显示、安装/升级回归 |
| 工作流与发布 | 依赖/权限契约及真实构建，核验发布的提交版本 |
| 纯文档 | 路径、链接和规则与现状一致；无需为文字改动新增镜像断言测试 |

行为测试是主要证据，源码字符串检查只作辅助。预期数量应来自同一身份规则下的完整目录，禁止为通过测试随意降低阈值。修复通用问题时覆盖至少一个失败或竞争场景；低影响的可逆改动不为凑覆盖率重复测试实现。

常规命令：

```sh
python -m pip install -r requirements-dev.txt
npm test
npm run check
npm run test:python
```

真实浏览器和 Windows 验证由相关工作流执行。报告中分别说明“目录发现、格式校验、实际播放、人工检查”，不得混为一谈。

## 11. 演进、例外与交付

新增机制先判断是否能通过现有数据或适配器表达。只有出现明确的新职责、生命周期或依赖边界时才新增服务；禁止为一次性差异引入复杂插件系统，也禁止单纯按文件长度拆分。

架构变更必须同步本规范和受影响入口。涉及依赖方向、身份语义、缓存迁移、引擎隔离或发布模式的决定，应在提交说明或 `docs/` 中记录：问题、选择、兼容策略、验证和剩余风险。临时兼容需注明退出条件，不能成为第二套默认实现。

提交前核对：

- 是否复用了注册表、身份策略、源适配和共同流水线？
- 新模块是否有明确职责、依赖和释放方式，是否引入了游戏名称分支或循环依赖？
- 旧 URL、模型 ID、收藏、缓存、资源目录和更新路径是否兼容？
- 失败、取消、资源版本变化及并发更新是否真实处理？
- 生成文件是否来自本次真实输入，审计是否保留失败？
- 验证是否足以支持报告结论，未覆盖范围是否写明？
- 文档、维护入口和自动检查是否与最终实现一致？

已知债务按[架构评审的迁移顺序](ARCHITECTURE_REVIEW_2026-10-23.md#后续迁移验收顺序)逐步偿还。规范要求不等于完成记录；不得仅靠移动文件或 CI 通过宣布全部架构债务已清除。

## 12. 仓库卫生与入口退役

依赖、字节码和临时产物不得提交；使用 `.gitignore` 与 `npm run audit:repo` 持续检查。清理前核对工作流、导入、数据、页面、测试与文档引用，并处理旧 URL 兼容。素材静态未引用仅是候选，动态路径、测试集和增量构建状态必须另行核实。退役后的历史实现由 Git 保存，不复制完整 backup/old 页面；兼容入口采用共同服务委托或跳转。具体保留与清理依据见 [仓库卫生记录](REPOSITORY_HYGIENE.md)。

## 13. 动态目录增量兼容

新增与重新导入使用工具侧共同的 `mergeCatalogRecords` / `merge_catalog_records`，按稳定 ID 合并，不按未经仓库限定的相对路径替换。跨目录重复 ID、同 ID 角色/皮肤/引擎冲突必须拒绝。默认保留既有来源、预览与无关记录；更新资源须逐 ID 显式指定 `--update-existing`，并清除旧预览证据。长时间来源扫描后重新读取目录，原子替换文件。

`catalog_compatibility.mjs` 比较完整注册目录、旧 ID、皮肤、资源地址、来源解释、去重后默认链接目标和预览保留情况；`--verify-previews` 继续核验文件存在与 SHA-256。兼容修复在 `data/catalog-compatibility-changes.json` 按 ID、字段和准确前后值记录原因；字段例外不能豁免预览校验。

`check_catalog_update.mjs` 在常规检查中使用实际 push / PR 基线，缺少浅克隆基线时补取该提交。CI 失败和导入器拒绝是具体保护边界，不等于未经核验的分支保护设置或所有外部写入路径均被强制阻止。见 [2026-10-25 兼容检查](CATALOG_COMPATIBILITY_REVIEW_2026-10-25.md)。
